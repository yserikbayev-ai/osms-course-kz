# Система обучения медперсонала по НПА РК (акцент — ОСМС)

**Дата:** 2026-08-02
**Владелец продукта:** Ержан Серикбаев (ИП «Серикбаев Ержан Оралбекович»)
**Статус:** дизайн согласован, готов к планированию реализации
**Источник знаний:** `База_знаний_НПА_МЗ_РК/` — 2479 актов Минздрава РК из ИПС «Әділет», выгрузка 2026-08-01

---

## 1. Что и зачем строим

Отдельный коммерческий продукт: веб-платформа обучения медперсонала нормативным
правовым актам РК, с тестами и уровнями. Первая тема — **ОСМС**.

**Модель продажи:** B2B. Клиника покупает лицензию на весь персонал. Ценность для
покупателя — руководитель видит, кто в команде действительно знает правила
финансирования, и располагает доказательством обучения персонала для проверок.

**Продукт отдельный от Medical CRM:** своя база, свой вход, своя лицензия. Продавать
можно в паре, но технической связи нет — иначе невозможно продать обучение тем, кто
не покупал CRM.

**Ключевое отличие от готовых LMS:** содержимое рождается из актуального
законодательства РК и само отслеживает его изменения. Конструктор курсов — не наше
преимущество и в продукт не входит.

### Принятые решения

| Вопрос | Решение |
|---|---|
| Цель | Отдельный продукт на продажу |
| Кто платит | Клиника (B2B), лицензия на персонал |
| Что такое «уровень» | Грейды сложности с последовательным допуском |
| Корректность контента | AI генерирует и публикует сразу, без ручной вычитки |
| Формат | Веб-платформа + Telegram для напоминаний |
| Язык | Русский (казахский — вне текущего скоупа) |
| Актуальность НПА | Автоматическое отслеживание изменений |
| Объём MVP | Вертикальный срез: одна тема (ОСМС) насквозь |

### Принятый риск

Публикация без ручной вычитки выбрана владельцем продукта осознанно, при
проговорённом риске. Смягчение, обязательное к реализации: каждый вопрос обязан
нести привязку к конкретной норме, иначе не публикуется; врачу доступна кнопка
«оспорить»; при накоплении жалоб вопрос автоматически замораживается. Формальный
валидатор отсекает механический брак, но **не** смысловые ошибки — единственный
контур их отлова — жалобы пользователей.

## 2. Архитектура

Семь компонентов с явными стыками, каждый разрабатывается и проверяется отдельно.

| Компонент | Назначение | Зависит от |
|---|---|---|
| Хранилище НПА | Read-only источник истины: 2479 `.md` + индекс | — |
| Контент-фабрика | Офлайн-конвейер: акты → нормы → уроки и вопросы | Хранилище НПА |
| Каталог обучения | БД: темы, грейды, уроки, банк вопросов, связь «вопрос → норма» | Контент-фабрика |
| Движок тестирования | Сборка теста, оценка, допуск, попытки | Каталог |
| Веб-кабинеты | Интерфейсы врача, главврача, администратора | Каталог, Движок |
| Notifier (Telegram) | Напоминания, вопрос дня, уведомления об изменениях | Каталог, Движок |
| Монитор НПА | Сверка с «Әділет», детект изменений, постановка на перегенерацию | Хранилище, Каталог |

**Размещение:** kz-сервер (`vpsza500.kz`). Обусловлено требованием законодательства РК
о хранении персональных данных внутри страны.

**Стек:** Python (FastAPI) + PostgreSQL + серверный рендеринг HTML. Выбран как
одноязычный и пригодный для самостоятельного сопровождения владельцем. Контент-фабрика
и монитор — отдельные процессы, а не часть веб-приложения: их сбой не должен ронять
обучение.

**Границы:** система не хранит медицинские данные пациентов и не связана с ДамуМед.
Работает только с текстами НПА и учебными результатами сотрудников.

**Расширяемость:** тема для фабрики и монитора — параметр. Добавление ГОБМП, тарифов
или стандартов не требует изменения кода, только нового манифеста темы.

## 3. Модель контента

### 3.1. Структура исходного материала

Замер на выборке 120 действующих актов:

| Тип акта | Доля | Обработка |
|---|---|---|
| С нумерованными пунктами (в среднем 54 пункта на акт) | 51 % | Нарезка по пунктам/подпунктам |
| Перечни и таблицы (коды, тарифы, состояния) | 24 % | Нарезка по строкам таблицы |
| Акты-изменения и отмены | 24 % | В обучение не идут; топливо для монитора |

### 3.2. Единица контента — «норма»

Норма = пункт (или строка перечня) с полным текстом и координатами: акт, номер
пункта, реквизиты, ссылка на источник.

Для перечней единицей служит строка вместе с заголовками столбцов — смысл содержится
именно в строке, отдельная ячейка его не несёт.

### 3.3. Манифест темы

Тема задаётся **курируемым списком актов**, а не поисковым запросом. Манифест ОСМС:
перечень ID актов с приоритетом (ядро: Кодекс о здоровье, правила ОСМС, правила
возмещения; периферия: смежные приказы).

Обоснование: слово «ОСМС» встречается в 150 действующих актах, но обучать по всем
150 бессмысленно — автоотбор по словам даёт мусор. Манифест — единственная точка,
требующая экспертного решения владельца, и он же делает добавление темы дешёвым.

### 3.4. Конвейер

1. Отбор актов по манифесту темы
2. Нарезка на нормы (по типу акта)
3. Отсев незначимого — процедурные пункты («контроль возложить на…», «вводится в
   действие по истечении…»)
4. Генерация: на каждую значимую норму — учебная карточка «что это значит на
   практике» + вопросы трёх грейдов
5. Формальная валидация
6. Дедупликация близких вопросов
7. Публикация в каталог

### 3.5. Валидатор (заменяет ручную вычитку)

Вопрос **не публикуется**, если выполнено хотя бы одно:

- нет привязки к конкретной норме
- верных ответов не ровно один
- варианты ответов дублируют друг друга
- вопрос проверяет номер или дату акта вместо содержания
- ответ не выводится из текста привязанной нормы
- правильный вариант заметно длиннее остальных (больше чем на 12 символов) —
  такой вопрос проходится по длине строки, без знания нормы
- неправильные варианты неправдоподобны: абсурдны, из другой темы или заведомо
  нелепы; все четыре варианта должны быть равнозначны по форме и объёму

Формальную часть (ровно четыре варианта, без повторов, без перекоса по длине)
проверяет `source/check_options.cjs` — он вызывается из `source/check.sh`.

### 3.6. Грейды на уровне вопроса

| Грейд | Что проверяет |
|---|---|
| Базовый | Знание нормы: что положено, кому, что входит в ОСМС |
| Продвинутый | Применение в коротком практическом кейсе |
| Экспертный | Пограничные ситуации, пересечение норм, последствия ошибки (снятие оплаты Фондом, дефектура) |

### 3.7. Объяснение и оспаривание

После ответа врач видит: правильный вариант, цитату нормы, реквизиты акта, ссылку на
источник, кнопку «оспорить». Жалоба уходит в очередь администратора; при накоплении
жалоб вопрос автоматически замораживается и не выдаётся до разбора.

### 3.8. Известное ограничение

В выгрузке сохранены ссылки **из** документов, но не якоря собственных пунктов
(`#zN`). Ссылка из вопроса ведёт на акт целиком; координата пункта хранится текстом.
Для MVP достаточно. Устраняется при следующем обновлении базы без изменений в
остальных компонентах.

## 4. Модель обучения

### 4.1. Структура

Курс = тема (ОСМС) → три грейда → уроки + экзамен грейда.

Урок: 5–9 карточек «норма → практика» + мини-проверка 3–5 вопросов. Мини-проверка
тренировочная, на допуск не влияет; её задача — исключить пассивное чтение.

### 4.2. Параметры экзаменов

Значения настраиваемые, не константы в коде.

| Грейд | Вопросов | Время | Порог |
|---|---|---|---|
| Базовый | 20 | 30 мин | 80 % |
| Продвинутый | 25 | 40 мин | 80 % |
| Экспертный | 30 | 50 мин | 80 % |

Выборка случайная из банка грейда; порядок вопросов и вариантов перемешивается.

Порог 80 % единый: для нормативных знаний 70 % означало бы, что каждый третий ответ
о деньгах Фонда неверен.

### 4.3. Допуск и попытки

- Следующий грейд открывается только после сдачи предыдущего
- Попыток — три
- После неудачной попытки назначаются **корректирующие действия** (см. 4.8)
- После третьей неудачи грейд блокируется до решения главврача — управленческий
  инструмент, не наказание

### 4.8. Корректирующие действия и измерение прогресса

Центральный цикл продукта (закреплён по прямому указанию владельца, голосовое
2026-08-02):

```
Тест → Корректирующие действия → Повторный тест → Прогресс
```

**Корректирующее действие** — именованная сущность, а не служебная деталь. После
неудачной попытки система:

1. Определяет нормы, по которым допущены ошибки
2. Формирует персональный список корректирующих действий: повторить конкретные уроки
   по этим нормам (не курс целиком)
3. Ставит паузу 24 часа перед повторной попыткой
4. Не допускает к повторному тесту, пока корректирующие действия не отмечены
   выполненными

**Прогресс** — главная метрика отчётности, а не просто факт сдачи. Хранится и
показывается дельта между попытками:

- результат первой попытки → результат повторной
- какие нормы были провалены и закрыты после корректирующих действий
- какие нормы остаются проблемными после повторной попытки (сигнал главврачу: это
  системный пробел, а не случайная ошибка)

Отчёт главврача строится вокруг этой дельты: ценность для покупателя — видеть не
«сдал/не сдал», а измеримое улучшение знаний команды и точки, где обучение не
сработало.

### 4.4. Сертификат

Выдаётся за все три грейда: PDF с ФИО, датой, перечнем тем и кодом проверки; по коду
открывается публичная страница подтверждения. Срок действия — 12 месяцев.

Истекающий сертификат — естественное основание для продления подписки.

### 4.5. Реакция на изменение законодательства

При изменении нормы, входящей в курс, врач получает не новый экзамен, а
**микро-обновление**: карточка «что изменилось» + 3–5 вопросов. Сертификат не
аннулируется, но получает статус «требует актуализации», видимый главврачу.

Механизм честнее аннулирования и создаёт постоянный поток активности в продукте.

### 4.6. Удержание

Telegram: напоминание о незавершённом грейде и «вопрос дня». Вопросы, в которых врач
ошибался, возвращаются чаще — простое интервальное повторение без сложной модели.

### 4.7. Ограничение

Удалённый тест не защищён от подсказок и совместного прохождения. Рандомизация,
таймер и большой банк повышают цену списывания, но не исключают его. Для B2B
приемлемо: заказчику нужна картина знаний команды. Юридически значимая аттестация
потребует очного прокторинга — вне текущего скоупа.

## 5. Роли и мульти-арендность

| Роль | Возможности |
|---|---|
| Врач | Курсы, уроки, экзамены, сертификат, история, оспаривание вопроса |
| Главврач | Сотрудники, назначение курсов, дашборд прогресса, разблокировка после трёх неудач, выгрузка отчёта |
| Администратор продукта | Клиники и лицензии, манифесты тем, запуск фабрики, очередь жалоб, заморозка вопросов |

Клиника — арендатор. Изоляция данных обеспечивается **на уровне каждого запроса**, а
не только интерфейса. Закладывается сразу: продукт проектируется на несколько клиник,
переделка изоляции задним числом дорога и опасна.

Минимальный набор экранов:

- **Врач:** Мои курсы · Урок · Экзамен · Результат · Сертификат
- **Главврач:** Сотрудники · Прогресс команды · Отчёт
- **Администратор:** Клиники · Темы · Жалобы · Запуски фабрики

## 6. Монитор НПА

Периодичность — раз в неделю.

1. Заново снимает выдачу поиска по Минздраву в «Әділет»
2. Сравнивает с сохранённым индексом: новые акты, сменившие статус на «Утративший
   силу», обновлённые редакции
3. Для актов из манифеста темы — перекачивает текст, сравнивает по нормам
4. Помечает вопросы, привязанные к изменившимся нормам → перегенерация
5. Порождает микро-обновления для врачей, прошедших затронутые уроки

### Обязательные требования к загрузчику

Извлечено из инцидента при первичной выгрузке 2026-08-01: при 6 параллельных потоках
adilet.zan.kz включил reCAPTCHA по IP и начал отдавать страницу-заглушку **с кодом
ответа 200**. Загрузчик принял её за валидный документ, из-за чего 2387 файлов
сохранились с корректными метаданными и пустым текстом. Блок держался 18 минут.

Требования (не «хорошая практика», а часть спецификации):

- Один поток, пауза 1–2 секунды между запросами
- Страница-капча распознаётся по содержимому и трактуется как ошибка, а не как
  пустой документ
- При обнаружении капчи — ожидание по нарастающей, без попыток обхода
- Документ с пустым телом не сохраняется, чтобы повторный запуск его дозагрузил
- Проверка сертификата TLS не отключается (у Python на машине владельца не проходит
  цепочка adilet — используется curl с системным хранилищем доверия)

## 7. Данные и безопасность

Хранятся персональные данные сотрудников: ФИО, должность, клиника, результаты
экзаменов. Медицинских данных пациентов нет — это сознательно снижает уровень риска
и объём требований.

- Размещение в Казахстане (закон РК о персональных данных)
- Согласие на обработку ПДн при регистрации
- Разграничение прав по ролям, минимально необходимые права
- Журнал действий: кто, что и когда сдавал

Журнал решает и прикладную задачу клиники — служит доказательством обучения персонала
при проверке.

---

## 8. Проверка качества

- **Автотесты:** нарезка норм, валидатор вопросов, правила допуска и оценки
- **«Золотой набор»:** несколько десятков эталонных норм с заранее известными
  свойствами; фабрика прогоняется по ним после каждого изменения промптов, чтобы
  деградация генерации не прошла незамеченной
- **Сквозной тест:** путь врача от регистрации до сертификата
- Нагрузочное тестирование не требуется: десятки пользователей на клинику

---

## 9. Критерии готовности MVP

1. Курс по ОСМС с тремя грейдами, банк не менее **300** прошедших валидацию вопросов
2. Полный путь врача работает: регистрация → уроки → экзамены → сертификат
3. Дашборд главврача показывает состояние команды
4. Монитор на реальном изменении нормы порождает микро-обновление
5. Telegram шлёт напоминания

**Первый арендатор:** ТОО «Моя Семейная амбулатория» — бесплатный пилот, обратная
связь до первой внешней продажи.

---

## 10. Вне скоупа

- Казахский язык
- Конструктор курсов, видео, произвольные материалы
- Очный прокторинг и юридически значимая аттестация
- Интеграция с Medical CRM и ДамуМед
- Темы помимо ОСМС (добавляются манифестами после MVP — по направлениям врачей:
  терапевт, гастроэнтеролог, УЗИ и далее; ОСМС остаётся сквозной темой для всех,
  поскольку правил финансирования касается каждый)
- Баллы НПР и признание сертификата государством

## 11. Открытые вопросы

1. **Цена лицензии** и её единица (за клинику / за сотрудника / за курс) — не
   определена, влияет на биллинг, но не на архитектуру MVP.
2. **Состав манифеста ОСМС** — конкретный перечень ID актов ядра требует решения
   владельца перед запуском фабрики.
3. **Модель LLM для генерации** и стоимость прогона на объёме темы — считается на
   этапе планирования.
